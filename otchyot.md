# Отчёт по лабораторной работе №2

**Тема:** Подключение базы данных и реализация CRUD через SQLAlchemy
**Вариант:** Интернет-магазин
**Сущность:** Товар (Product)

---

## Цель работы

Научиться подключать базу данных к FastAPI-приложению и реализовывать операции создания, чтения, обновления и удаления с использованием SQLAlchemy.

---

## Ход выполнения работы

### 1. Структура проекта
Проект организован по слоям:
- `app/api/` — маршруты (эндпоинты);
- `app/core/` — конфигурация;
- `app/db/` — подключение к базе данных;
- `app/models/` — модели SQLAlchemy;
- `app/schemas/` — Pydantic-схемы;
- `app/services/` — слой бизнес-логики;
- `app/main.py` — точка входа приложения.

### 2. Настройка конфигурации
Создан файл `.env`, в котором задана строка подключения к базе данных: `DATABASE_URL=sqlite+aiosqlite:///./shop.db`. Настройки читаются через `pydantic-settings` в `app/core/config.py` (класс `Settings`). Файл `.env` добавлен в `.gitignore`, чтобы секреты не попадали в репозиторий.

### 3. Подключение базы данных
В файле `app/db/base.py` объявлен базовый класс `Base` (наследник `DeclarativeBase`).
В файле `app/db/session.py` создан асинхронный движок `create_async_engine` и фабрика сессий `async_sessionmaker`. В качестве СУБД используется SQLite через драйвер `aiosqlite`. Также была установлена библиотека `greenlet`, необходимая для асинхронной работы SQLAlchemy.

### 4. Модель базы данных
В файле `app/models/product.py` описана модель `Product` для таблицы `products` со следующими колонками:
- `id` — первичный ключ;
- `title` — название товара (индексируемое);
- `description` — описание;
- `price` — цена;
- `stock` — количество на складе;
- `created_at` — дата создания.

### 5. Pydantic-схемы
В файле `app/schemas/product.py` описаны схемы `ProductBase`, `ProductCreate` и `ProductRead`. Валидация гарантирует, что цена (`price`) всегда больше нуля, а название не пустое. Модель базы данных и Pydantic-схемы строго разделены.

### 6. Слой сервиса (взаимодействие с БД)
В файле `app/services/product.py` создан класс `ProductService`, который принимает асинхронную сессию. В нём реализованы методы `list()`, `get()`, `create()`, `update()` и `delete()`. Все методы асинхронные и работают через `AsyncSession`.

### 7. Зависимости FastAPI
В файле `app/api/deps.py` описана зависимость `get_db`, которая создает асинхронную сессию, отдает её в маршрут и автоматически закрывает после завершения обработки запроса.

### 8. CRUD-маршруты
В файле `app/api/v1/products.py` реализованы пять эндпоинтов (GET, GET by id, POST, PUT, DELETE). Возвращаются корректные статус-коды: `201` при создании, `204` при удалении, `404` при отсутствии объекта.

### 9. Инициализация базы данных
В файле `app/main.py` реализован `lifespan`-контекст, который при старте приложения автоматически создает все необходимые таблицы в базе данных (`Base.metadata.create_all`).

## Выводы

В ходе лабораторной работы было освоено подключение реляционной базы данных к приложению на FastAPI с использованием асинхронного драйвера SQLAlchemy. Реализован полноценный CRUD-интерфейс для сущности «Товар». 

Код был успешно разделён на слои: модели данных (SQLAlchemy), схемы валидации (Pydantic), слой бизнес-логики (сервисы) и маршруты. # Отчёт по лабораторной работе №3

**Тема:** Управление схемой базы данных с помощью Alembic  
**Вариант:** Интернет-магазин

## Цель работы
Получить навыки управления структурой базы данных с помощью миграций.

## Ход выполнения работы

### 1. Подключение и настройка Alembic
Ранее библиотека Alembic была установлена в виртуальное окружение. Файл конфигурации `alembic.ini` и папка `migrations` были инициализированы командой:

```bash
alembic init migrations
```

В файле `alembic.ini` была закомментирована строка `sqlalchemy.url`, чтобы Alembic не использовал жестко заданный URL, а брал настройки из переменных окружения.

### 2. Настройка файла `migrations/env.py`
Файл `migrations/env.py` был полностью переписан. В нём:
- Импортирован объект `settings` из `app.core.config`, чтобы брать URL базы данных из файла `.env`.
- Импортирован базовый класс `Base` из `app.db.base` и модель `Product` из `app.models.product`.
- URL базы данных передается в Alembic через `config.set_main_option`, при этом из строки подключения убирается префикс `+aiosqlite`, так как Alembic выполняет миграции в синхронном режиме.
- Использован стандартный подход для работы с async SQLAlchemy с вызовом `connectable.connect()` и `context.configure()`.

### 3. Добавление нового поля в модель
По заданию лабораторной работы в модель `Product` (файл `app/models/product.py`) было добавлено новое поле `status` (статус товара), которое по умолчанию принимает значение `"active"`. Тип поля — строка (`String(20)`). Также были обновлены Pydantic-схемы в `app/schemas/product.py`: поле `status` добавлено в `ProductBase` и `ProductUpdate`.

### 4. Отказ от автоматического создания таблиц
Так как теперь структура базы данных управляется исключительно через миграции, из файла `app/main.py` был удален вызов `Base.metadata.create_all`. В контексте `lifespan` оставили только корректное закрытие соединений `await engine.dispose()`.

### 5. Создание и применение миграции
Так как ранее база данных создавалась автоматически, старый файл `shop.db` был удален, чтобы Alembic начал управление схемой с чистого листа. Была сгенерирована первая миграция на основе моделей командой:

```bash
python -m alembic revision --autogenerate -m "create products table"
```

Alembic обнаружил таблицу `products` и создал файл миграции в папке `migrations/versions`. Миграция была успешно применена к базе данных командой:

```bash
python -m alembic upgrade head
```

Таблица `products` была создана непосредственно Alembic. Также был проверен откат миграции (`alembic downgrade -1`) и её повторное применение.

## Проверка работоспособности
После запуска сервера (`uvicorn app.main:app --reload`) и перехода в Swagger UI:
- Был создан новый товар через `POST /api/v1/products`. В ответе (код `201 Created`) присутствует новое поле `"status": "active"`.
- Данные корректно сохраняются в базу данных, управляемую Alembic, и не пропадают после перезапуска сервера.

## Выводы
В ходе лабораторной работы было освоено управление схемой базы данных с помощью Alembic. Подключение Alembic к асинхронному FastAPI-приложению потребовало настройки файла `env.py` для использования синхронного движка и чтения настроек из файла `.env`. Было добавлено новое поле в модель данных и сгенерирована соответствующая миграция. Использование миграций позволяет безопасно изменять структуру таблиц и откатывать изменения, что критически важно для командной разработки и развертывания приложения на разных серверах. Автоматическое создание таблиц при старте приложения было отключено.

# Отчёт по лабораторной работе №4

**Тема:** Связи между сущностями, пагинация, фильтрация и сортировка  
**Вариант:** Интернет-магазин  
**Сущности:** Товар (`Product`), Категория (`Category`)

## Цель работы
Научиться проектировать связи между сущностями (на примере связи «Один ко многим»), реализовывать выборку связанных данных, а также предоставлять удобные средства получения списков (пагинация, фильтрация и сортировка).

## Ход выполнения работы

### 1. Проектирование связей
Для предметной области «Интернет-магазин» была выбрана связь «Один ко многим» (One-to-Many): у одной категории может быть много товаров, но каждый товар принадлежит только одной категории. Для реализации этой связи мы создали новую сущность `Category` (Категория) и добавили в модель `Product` внешний ключ `category_id`, который ссылается на таблицу `categories`.

### 2. Добавление модели Категории
В файле `app/models/category.py` была создана модель `Category` с полями `id` и `name` (название категории). В модели `Product` (в файле `app/models/product.py`) было добавлено поле `category_id` (внешний ключ) и связь с категорией через `relationship`.

### 3. Миграции Alembic (решение проблемы SQLite)
При генерации миграции с помощью Alembic возникла ошибка, связанная с тем, что SQLite не поддерживает команду `ALTER` для добавления внешних ключей в уже существующую таблицу. Для решения этой проблемы мы включили режим `render_as_batch=True` в файле `migrations/env.py`. Это заставило Alembic создавать новую таблицу с нужными связями, копировать туда данные и удалять старую. 

Также вручную пришлось задать имя для внешнего ключа (`fk_products_category_id`) в файле миграции, так как SQLite требует явных имен для ограничений. В итоге миграция была успешно применена командой:

```bash
alembic upgrade head
```

### 4. Обновление Pydantic-схем
В файле `app/schemas/category.py` были описаны схемы для создания и чтения категорий (`CategoryCreate`, `CategoryRead`). В файле `app/schemas/product.py` в схему `ProductRead` был добавлен вложенный объект `category`, чтобы клиент при получении товара сразу видел данные его категории. Также в `ProductBase` было добавлено поле `category_id`.

### 5. Реализация пагинации, фильтрации и сортировки
Для работы со списками в файле `app/services/product.py` был переписан метод `paginate`. В нём реализовано:
- Пагинация через смещение (`offset`) и лимит (`limit`), а также подсчет общего количества записей (`total`).
- Сортировка через метод `order_by()`. Поле сортировки и направление (`asc`/`desc`) передаются динамически.
- Фильтрация через метод `where()`. Добавлены фильтры по категории (`category_id`), статусу (`status`) и поиску по названию (`search`).

Для решения проблемы N+1 (когда для получения категории каждого товара делается отдельный SQL-запрос) в запросе используется жадная загрузка `selectinload(Product.category)`.

### 6. Создание эндпоинтов для категорий и обновление роутера товаров
Был создан файл `app/api/v1/categories.py` с двумя эндпоинтами: `GET /api/v1/categories` (список) и `POST /api/v1/categories` (создание).

В файле `app/api/v1/products.py` маршрут `GET /api/v1/products` был обновлен. Теперь он принимает Query-параметры: `page` и `size` (пагинация), `sort_by` и `order` (сортировка), `category_id`, `status` и `search` (фильтрация). Ответ возвращается в формате объекта с полями `items`, `total`, `page`, `size`, `pages` (схема `Page`).

## Выводы
В ходе лабораторной работы мы научились проектировать связи между таблицами в базе данных и отражать их в ORM SQLAlchemy. Мы успешно реализовали связь «Один ко многим» между категориями и товарами.

Кроме того, мы значительно расширили функционал API: внедрили пагинацию, сортировку и фильтрацию для списка товаров. Использование `selectinload` позволило избежать проблемы N+1 и оптимизировать запросы к базе данных.

Из-за ограничений SQLite пришлось освоить работу с `batch_alter_table` в Alembic, что является важным практическим навыком. Теперь наше API готово к работе с большими объемами данных и предоставляет клиенту удобный интерфейс для поиска и просмотра товаров.


# Отчёт по лабораторной работе №5

**Тема:** Аутентификация и авторизация  
**Вариант:** Интернет-магазин  
**Реализованные сущности:** Пользователь (`User`)

## Цель работы
Реализовать систему регистрации, входа, защиты маршрутов и разграничения прав доступа с использованием JWT-токенов и хэширования паролей.

## Ход выполнения работы

### 1. Установка зависимостей
Для реализации аутентификации были установлены библиотеки:
- `passlib[bcrypt]` — для безопасного хэширования паролей;
- `python-jose[cryptography]` — для генерации и проверки JWT-токенов;
- `pydantic[email]` — для валидации email-адресов.

### 2. Настройка конфигурации и безопасности
В файл `.env` были добавлены секретные параметры (`APP_SECRET_KEY`, `ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES`). Они читаются через `pydantic-settings` в файле `app/core/config.py`.

В файле `app/core/security.py` реализованы функции:
- `hash_password` — хэширование пароля перед сохранением в БД (алгоритм bcrypt).
- `verify_password` — проверка пароля при входе.
- `create_access_token` — генерация JWT-токена с идентификатором пользователя и временем истечения.
- `decode_token` — декодирование и проверка токена.

### 3. Модель Пользователя
Создана модель `User` (в `app/models/user.py`) со следующими полями: `id`, `email` (уникальный), `hashed_password`, `full_name`, `role` (роль: `admin`, `manager` или `user`) и `created_at`. С помощью Alembic сгенерирована и применена миграция для создания таблицы `users`.

### 4. Схемы и Сервис
В файле `app/schemas/user.py` созданы Pydantic-схемы: `UserRegister` (для регистрации), `UserLogin` (для входа), `UserRead` (для ответа без пароля) и `Token` (для возврата токена).

В файле `app/services/auth.py` реализован класс `AuthService` с методами `register` (создание пользователя с хэшированием пароля) и `authenticate` (проверка пароля при входе).

### 5. Реализация эндпоинтов аутентификации
Создан файл `app/api/v1/auth.py` с маршрутами:
- `POST /api/v1/auth/register` — создает нового пользователя.
- `POST /api/v1/auth/login` — проверяет пароль и выдает JWT-токен (`access_token`).

Создан файл `app/api/v1/users.py` с маршрутом `GET /api/v1/users/me`, который возвращает данные текущего авторизованного пользователя.

### 6. Зависимость для защиты маршрутов (Авторизация)
В файле `app/api/deps.py` добавлена зависимость `get_current_user`. Она извлекает JWT-токен из заголовка `Authorization`, декодирует его, достает ID пользователя, находит его в базе и возвращает объект пользователя. Если токен отсутствует или невалиден, FastAPI возвращает ошибку `401 Unauthorized`.

### 7. Разграничение прав доступа (Роли)
В файле `app/api/deps.py` также реализована функция `require_role`, которая проверяет роль текущего пользователя.

Маршруты изменения данных (`POST`, `PUT`, `DELETE`) в файлах `app/api/v1/products.py` и `app/api/v1/categories.py` были защищены зависимостью `require_role("admin", "manager")`. Теперь создавать и изменять товары и категории могут только администраторы и менеджеры. Обычным пользователям возвращается ошибка `403 Forbidden`.

## Выводы
В ходе лабораторной работы была успешно реализована система безопасности API. Освоено хэширование паролей с помощью алгоритма bcrypt и генерация JWT-токенов для stateless-аутентификации.

Реализованы механизмы защиты маршрутов с помощью внедрения зависимостей FastAPI. Настроена ролевая модель (RBAC), позволяющая разграничивать уровень доступа. Теперь изменение данных в интернет-магазине доступно только авторизованным пользователям с соответствующей ролью, что защищает систему от несанкционированных действий.


# Отчёт по лабораторной работе №6

**Тема:** Работа с файлами и фоновыми задачами  
**Вариант:** Интернет-магазин  
**Реализованные сущности:** Вложение (`Attachment`)

## Цель работы
Получить навыки загрузки файлов на сервер, проверки их типа и размера, а также использования фоновых задач для операций, не требующих немедленного ответа.

## Ход выполнения работы

### 1. Подготовка зависимостей и модели данных
Для работы с формами и файлами в FastAPI используется библиотека `python-multipart`. Для хранения файлов была создана директория `uploads/` в корне проекта.

Была создана модель `Attachment` (в файле `app/models/attachment.py`) для хранения метаданных файла. Бинарные данные (сами файлы) в базе данных не хранятся — только информация о них:
- `id` — идентификатор записи;
- `product_id` — внешний ключ на товар;
- `filename` — оригинальное имя файла;
- `file_path` — путь на сервере;
- `content_type` — MIME-тип;
- `size` — размер в байтах;
- `created_at` — дата и время загрузки.

С помощью Alembic была сгенерирована и применена миграция для создания таблицы `attachments`.

### 2. Слой схем и фоновые задачи
В файле `app/schemas/attachment.py` описана Pydantic-схема `AttachmentRead` для возврата метаданных клиенту.

В файле `app/tasks.py` создана функция `log_upload_event`, которая имитирует долгую операцию (например, отправку уведомления администратору) и пишет лог в консоль через модуль `logging`.

### 3. Реализация загрузки файлов (`UploadFile`)
В файле `app/api/v1/attachments.py` реализован эндпоинт `POST /api/v1/products/{product_id}/attachments` для прикрепления файла к товару.

В процессе обработки запроса выполняются следующие шаги:
- **Проверка расширения:** запрещены опасные расширения (`.exe`, `.bat`, `.sh`, `.cmd`). Если файл содержит одно из них, возвращается ошибка `400 Bad Request`.
- **Проверка размера:** если файл превышает лимит (5 МБ), возвращается ошибка `413 Request Entity Too Large`.
- **Проверка MIME-типа:** разрешены только изображения, PDF и текстовые файлы.
- **Сохранение файла:** файл сохраняется в директорию `uploads/` с уникальным именем (генерируется через `uuid4`), чтобы избежать конфликтов имен.
- **Сохранение метаданных:** в базу данных записываются имя, путь, тип и размер файла.

### 4. Реализация фоновой задачи
В эндпоинте загрузки файла добавлена зависимость `BackgroundTasks`. После успешного сохранения файла и метаданных вызывается метод `background.add_task(log_upload_event, ...)`. Это означает, что клиент мгновенно получает ответ `201 Created`, а задача выполняется сервером в фоне уже после отправки ответа.

## Выводы
В ходе лабораторной работы была освоена работа с файлами в FastAPI. Реализована безопасная загрузка вложений с проверкой расширения, размера и MIME-типа. Файлы сохраняются на диске, а в базе данных хранятся только их метаданные, что является правильной архитектурной практикой, позволяющей не раздувать базу данных.

Кроме того, были изучены механизмы фоновых задач (`BackgroundTasks`), которые позволяют разгрузить время ответа сервера и выполнять тяжелые операции (например, логирование или отправку уведомлений) в фоне, не заставляя пользователя ждать.

# Отчёт по лабораторной работе №8

**Тема:** Архитектура приложения: сервисы, репозитории и обработка ошибок  
**Вариант:** Интернет-магазин

## Цель работы
Научиться разделять ответственность между слоями приложения (маршруты, сервисы, репозитории) и реализовать единый централизованный формат возврата ошибок.

## Ход выполнения работы

### 1. Создание единого формата ошибок
По умолчанию FastAPI возвращает ошибки в формате `{"detail": "..."}`. По требованиям методички мы привели все ошибки к единому стандарту:

```json
{
  "error": {
    "code": "...",
    "message": "...",
    "details": {}
  }
}
```

Для этого был создан файл `app/core/exceptions.py`, содержащий два глобальных обработчика:
- `http_exception_handler` — перехватывает все ошибки HTTP (`401`, `403`, `404`, `400`).
- `validation_exception_handler` — перехватывает ошибки валидации Pydantic (`422`).

Они были подключены к приложению в файле `app/main.py` с помощью `app.add_exception_handler(...)`.

### 2. Настройка логирования
В файле `app/core/logging.py` была настроена функция `setup_logging()`, которая использует стандартный модуль `logging` для вывода логов в консоль. Логирование было включено в `app/main.py`. Теперь при создании товара в сервисе пишется лог через `logger.info(...)`.

### 3. Вынос работы с БД в слой репозиториев
Ранее запросы к базе данных (`select`, `commit`) находились прямо в сервисах. Теперь для этого создан отдельный слой:
- Создан базовый класс `BaseRepository` (в `app/repositories/base.py`), который содержит общие методы: `get`, `create`, `delete`.
- Создан класс `ProductRepository` (в `app/repositories/product.py`), который наследуется от базового и реализует специфичные методы: `get_with_category` (с жадной загрузкой) и `paginate` (с фильтрацией и сортировкой).

Теперь репозиторий отвечает исключительно за общение с базой данных и не содержит бизнес-правил.

### 4. Вынос бизнес-логики в сервисный слой
В файле `app/services/product.py` был переписан класс `ProductService`. Теперь в конструктор класса внедряется `ProductRepository`.

Сервис больше не знает, как работает SQLAlchemy — он вызывает методы репозитория. При этом в сервисе реализована бизнес-логика: проверка ролей пользователя (`admin`, `manager`). Если роль не подходит — выбрасывается исключение `PermissionError`, которое затем перехватывается в маршруте.

### 5. Внедрение зависимостей (DI)
В файле `app/api/deps.py` были добавлены функции `get_product_repo` (создаёт репозиторий) и `get_product_service` (создаёт сервис, передавая в него репозиторий). Теперь FastAPI сам собирает эту цепочку зависимостей.

### 6. «Тонкие» маршруты
Файл `app/api/v1/products.py` был переписан. Теперь маршруты не знают о базе данных (о репозиториях) и не содержат проверок ролей. Они просто принимают запрос, вызывают метод сервиса и возвращают результат или выбрасывают `HTTPException` (который потом перехватывается глобальным обработчиком).

## Выводы
В ходе лабораторной работы была проведена серьезная работа по улучшению качества кода. Мы внедрили многослойную архитектуру: маршруты стали «тонкими» (отвечают только за HTTP), бизнес-логика переехала в сервисный слой, а работа с БД — в репозитории.

Был настроен сбор логов через стандартный модуль `logging` и реализован единый формат возврата ошибок для всего API. Использование внедрения зависимостей (DI) позволило сделать код модульным и легко тестируемым, что подтвердилось успешным прохождением всех 6 интеграционных тестов после рефакторинга.
